# Performance

This document records how the rewrite was measured, what the numbers are, where
the time goes, and which optimizations were kept (including the single `unsafe`
block and why it is justified).

Reproduce everything with:

```sh
make dist
make bench                       # Rust vs Ruby, Markdown table
python3 bench/run_bench.py --threads 1   # single-core comparison
```

## Test environment

| | |
|---|---|
| CPU | 4 logical cores available to the container |
| OS | Linux 6.x, x86_64 |
| Rust | stable 1.99.1, `x86_64-unknown-linux-musl`, `opt-level=3`, LTO, `codegen-units=1` |
| Ruby | 3.4 (substitution cases use `tests/parity/oracle_compat.rb`) |
| Timer | `hyperfine 2.0.0`, min of N runs, `max_rss` for memory |

The host was **busy** during measurement (`/proc/loadavg` between 3 and 6 on 4
cores), so absolute times are pessimistic and noisy. For every case the table
reports the *minimum* wall time, which is the most robust statistic under load.
Correctness is unaffected; see the parity gate in the README.

### Startup latency

The tiny invocation is dominated by process start-up, dataset lookup and
option parsing — the case where a one-shot CLI lives or dies.

| | Rust (static musl) | Ruby |
|---|---|---|
| `username-anarchy anna key` | **0.8 ms** | 198 ms |
| `--help` | ~0.7 ms | ~180 ms |

Two factors matter:

* **No interpreter.** Ruby spends ~150 ms booting the interpreter and loading
  `optparse`/`set`/`pp` before it parses a single argument.
* **Static linking.** The binary has no `PT_INTERP` and no `DT_NEEDED` entries,
  so the dynamic loader does no work at all. A static-PIE executable still gets
  ASLR; the kernel maps it directly.

The default run (`anna key`) touches only in-tree literals and never reads a
dataset, so start-up cost is essentially `execve` + parsing 24 static plugins.

### Throughput

The 10k/100k cases use generated input files (`bench/data/`), two name columns
per row, and the full default plugin set. Output is de-duplicated globally, so
the 100k rows produce 463,073 unique lines.

Substitution cases use the Facebook top-1000 given/family lists with a single
empty person, so `%givenname` and `%surname` each expand to 1000 values:

* **full**: 1,000,000 substitutions written (999,824 unique lines);
* **`-m 5`**: the same expansion, truncated to 6 results.

The `-m 5` speedup (~3,300×) is larger than the others because Rust enumerates
lazily and stops after the requested number of substitutions, while Ruby builds
the entire one-million-element array and only then slices it. This is not a
parity shortcut: `-m` is defined as "keep the first N results", and the first N
of the ordered enumeration are exactly Ruby's first N (verified by the harness).

## Memory

| Case | Rust peak RSS | Ruby peak RSS |
|---|---:|---:|
| tiny | 3.3 MiB | 14.9 MiB |
| 10k rows | 5.0 MiB | 28.2 MiB |
| 100k rows | 41.3 MiB | 112.9 MiB |
| 1M substitutions | 49.1 MiB | 226.7 MiB |

Rust stores each unique output line once in a contiguous arena plus an 8-byte
`(offset, len)` record and one open-addressed table slot. Ruby keeps a
`Set` of `String`s plus the fully materialised expansion array, which is why
the substitution case is ~4.6× larger.

## Where the time goes

Profiling used `perf record -e cpu-clock` (hardware PMU events are not exposed
in this container) on the 100k-row case.

### First working version

A straightforward port used `FxHashSet<Vec<u8>>` behind 64 sharded `Mutex`es.
Sample distribution:

```
19.6%  memcpy
15.5%  Emitter::emit            (build case-folded key, lock shard)
15.1%  __libc_free
12.5%  __libc_malloc_impl
 4.7%  alloc_slot
 4.4%  RawTable::reserve_rehash
 4.3%  ...
```

Two problems:

1. **A heap allocation per candidate.** `set.insert(key.to_vec())` allocates
   before it knows the line is a duplicate. With a ~75% duplicate rate that is
   ~1.9M allocations for 463k unique lines.
2. **Allocation on every format fragment.** `String#downcase`-equivalent calls
   returned a fresh `Vec` for each template segment (~6M allocations).

### After optimization

```
20.4%  Sink::insert             (hash + open-addressed probe + grow)
13.8%  util::downcase_into
 9.9%  fmt::resolve_string
 9.4%  __libc_malloc_impl
 8.7%  __libc_free
 6.3%  fmt::tokenize
 5.8%  engine::gen_people
 5.0%  alloc_slot
 4.4%  memcpy
 2.5%  fmt::val
 2.2%  memcmp
```

`memcpy` fell from 17.8% to 4.4% and total CPU dropped by roughly a third. The
remaining allocation traffic is mostly `Name::init` clones and expansion
temporaries; the dedup path is allocation-free for duplicates.

## Optimizations kept

1. **Arena de-duplication with an open-addressed table** (`src/engine.rs`).
   Unique line bytes live in one `Vec<u8>`; an `(offset, len)` record per line
   preserves emission order; a power-of-two table of `(hash tag, entry index)`
   gives O(1) membership. A duplicate costs one hash, one cache-line probe and a
   byte comparison — no allocation. Storing the tag inline avoids the second
   indirection a `HashMap<u64, index>` needs.

2. **No locks on the hot path.** Workers own their sink outright. The parallel
   path generates per-chunk sinks and merges them once at the end, so there is
   no mutex traffic or shared-cacheline ping-pong while generating.

3. **In-place case folding and fragment appends** (`src/util.rs`,
   `src/fmt.rs`). `downcase_into`, `upcase_it_into` and `push_bytes` append into
   a reusable buffer instead of returning `Vec`s. This removed the per-segment
   allocations.

4. **Lazy enumeration for `-m`** (`src/fmt.rs`). The odometer stops after
   `max_sub + 1` results instead of materialising the full cartesian product.
   Verbose counts still report the full product, matching the original.

5. **Fast paths for the common case.** `tokenize` returns an empty `Vec`
   (no allocation) when the resolved string has no `%`; the non-case-insensitive
   path inserts the caller's slice directly; ASCII checks gate the Unicode
   fallbacks.

6. **Small-copy fast path** — the only `unsafe` block (see below).

## The single `unsafe` block

`src/util.rs::push_bytes` appends up to 16 bytes with constant-size
`ptr::copy_nonoverlapping` calls (8+8, 4+4, 2+2, 1) instead of calling
`memcpy`. `perf` attributed ~18% of a run to `memcpy` almost entirely from
these short appends; after the change it is ~4.4%.

Safety argument (also in the source):

* `out.reserve(s.len())` guarantees capacity for the whole copy;
* the overlapping-tail trick keeps every write inside `[len, len + s.len())`;
* `s` never aliases `out` (all call sites pass independent buffers);
* `set_len` only exposes bytes that were just initialised.

This is deliberately isolated in one function with a documented contract. The
rest of the program is safe Rust; `#![forbid(unsafe_code)]` cannot be used
because of this function, but no other module contains `unsafe`.

## Why not `memchr`/`regex`?

The format strings are tiny (≤ 20 bytes) and compiled once into a segment
list at start-up. A hand-written scanner beats a regex engine on inputs this
short, and avoids a dependency. Long literals are copied with `memcpy`.

## musl vs glibc

The shipped target is `x86_64-unknown-linux-musl`, built with rustc's bundled
musl and `+crt-static` (no `musl-gcc` linker override). The result is
`static-pie`, with no `PT_INTERP` and zero `DT_NEEDED` entries, so it runs on any
x86_64 Linux kernel regardless of the installed libc.

No measurable performance difference was observed between the musl static build
and a glibc dynamic build for this workload — it is dominated by hashing,
bytes and `write(2)`, not by libc string routines. The static build is preferred
because it removes the loader entirely and makes start-up deterministic.

## Scaling limits

The tool is in-memory and de-duplicates globally, as the original does.

* Ad-hoc input lists and wordlists: fine into the low millions of lines.
* `--auto --country <cc>`: the publicprofiler lists are small (tens per
  country), so the cross-product is trivial.
* `--auto` with the default Facebook dataset is 10,000 × 10,000 = **10^8
  people**. Neither implementation can finish that in reasonable time or
  memory, and Ruby is far worse. Use `-m`, `-f`, or explicit wordlists to bound
  the work. This is a property of the original design, not of the rewrite.
* The dedup arena uses 32-bit offsets, i.e. up to 4 GiB of unique output
  (hundreds of millions of short lines). Beyond that the assumption is checked
  in debug builds; the documented scope is far below it.

## Parallelism

Above ~200,000 estimated candidates the work is split across
`available_parallelism()` cores. Two environment variables make this testable:

```sh
USERNAME_ANARCHY_THREADS=1          # force serial
USERNAME_ANARCHY_MIN_PARALLEL=0     # force parallel even for tiny inputs
```

Measured on the loaded 4-core host, the 100k case went from ~1.65 s (1 thread)
to ~1.33 s (2 threads); 4 threads was slower because the host was already
saturated. On an idle machine the chunked, lock-free design scales close to
linearly until memory bandwidth becomes the limit. Ordering is not part of the
output contract, and the merge is deterministic per chunk.

## Correctness vs speed

Every optimization was validated against the 411-case parity gate
(`make test`), including cases specifically constructed to exercise the
optimized paths:

* expansion ordering and `-m` truncation (odometer order must match Ruby's),
* token reassembly in custom `-F` formats (round-based engine),
* global dedup across people and plugins,
* empty/CRLF/no-trailing-newline inputs,
* case folding + suffix ordering,
* invalid countries, invalid formats and other error paths.
